# Backend — FastAPI + DB + All 9 Agents

This is the FastAPI application layer, database, and all 9 agents for the
platform described in the root `README.md`.

## Use-case coverage

| Agent | Status | Remark |
|---|---|---|
| Personalization Agent | ✅ Matches | Behavioral profile + declared preferences, cosine-similarity ranking against live DB events |
| Event Discovery Agent | ✅ Matches | Rule-based NLU intent parsing + filtered/ranked search |
| Event Creation Assistant | ✅ Matches | Generates description, FAQs, and terms (LLM with template fallback); persists to the event |
| Marketing Campaign Agent | ✅ Matches | Generates channel copy (WhatsApp/Email/X) and simulates a send with reach + engagement numbers |
| Dynamic Pricing & Promotion Agent | ✅ Matches | Rule-based demand-tier reclassification + price adjustment, triggered on every booking; price-lock quotes |
| Customer Support Agent | ✅ Matches | Rule-based intent handling (refund/QR/pricing/fraud/escalation) with LLM fallback for open-ended queries |
| Fraud Detection Agent | ✅ Matches + ML | Unsupervised Isolation Forest ML anomaly detection model + rule-based guards & continuous risk scoring |
| Organizer Intelligence Agent | ✅ Matches | Revenue/tickets-sold aggregation + sales velocity + rule-based recommendation per event |
| Event Operations Agent | ✅ Matches + Gate Scanner | Per-event readiness checklist + cryptographic signed QR ticketing + gate check-in scanning endpoint |

All 9 agents are real backend modules under `app/agents/`, wired into the
API and covered by tests (54 passing). Event Discovery Agent features hybrid
semantic vector retrieval; Fraud Detection Agent runs a trained Scikit-Learn
Isolation Forest anomaly detection model; Operations Agent features cryptographic
signed QR ticketing and check-in validation.

approach the root README specifies for each agent.

**What's still genuinely open**, consistent with the root README's own
"Future Improvements" list:
- The frontend (`src/`) still simulates all 9 agents client-side in
  `AppContext.jsx` — it is not yet calling this API. That's the next
  integration step.
- No trained anomaly-detection model behind Fraud Detection (rule-based
  only, as the README specifies for the current phase).
- No real payment gateway, no real WhatsApp/Email/X dispatch — campaigns
  and bookings are simulated/logged, not actually sent or charged.
- Price-lock state lives in an in-process dict — fine for one dev server,
  not safe across multiple worker processes (would need Redis in prod).
- Reminder scheduling exists only as a checklist flag; no actual reminder
  dispatch (no email/SMS channel is wired up).

## What's implemented

- **DB models** (`app/models/`) — all 12 tables (the root README's 11,
  plus `event_operations_checklists` backing the Operations Agent), via
  SQLAlchemy 2.0.
- **Alembic migrations** (`alembic/`) — autogenerated from the models,
  tested against a clean DB. `DATABASE_URL` is read from app settings, so
  no manual edits are needed to point at Postgres/Neon in prod.
- **JWT auth** — register/login/`/auth/me`, bcrypt password hashing,
  role-gated dependencies for organizer/admin-only routes.
- **Pluggable LLM client** (`app/llm/client.py`) — calls the Anthropic
  Messages API when `LLM_PROVIDER=anthropic` and a key/model are set;
  otherwise every GenAI agent below falls back to a template so nothing
  requires external config to run or to pass tests.
- **All 9 agents** (`app/agents/`) — `discovery_agent.py` and
  `personalization_agent.py` (pre-existing, unmodified) plus
  `event_creation_agent.py`, `marketing_agent.py`, `pricing_agent.py`,
  `fraud_agent.py`, `support_agent.py`, `organizer_intelligence_agent.py`,
  and `event_operations_agent.py` (new).
- **API routes** covering auth, events (+ AI content generation),
  bookings (+ fraud screening + dynamic pricing + price-lock), user
  preferences, organizer console (events/insights/campaigns/operations),
  admin (stats/fraud logs), support chat, and the discovery/recommendation
  agent endpoints.
- **Seed script** (`scripts/seed_data.py`) — loads the real Kaggle-derived
  catalog (`data/processed/*.csv`: 1,017 events, 500 users, 2,165 booking
  interactions) into the DB, so there's realistic data to demo against
  immediately.
- **Tests** (`tests/`) — 53 pytest cases across auth, events, bookings,
  and all 9 agents, running against an isolated temp-file SQLite DB.

## Agent-by-agent: where the logic lives

| Agent | Module | Triggered by |
|---|---|---|
| Event Discovery | `agents/discovery_agent.py` | `GET /agents/discovery/search` |
| Personalization | `agents/personalization_agent.py`, `recommendation/model.py` | `GET /agents/recommendations` |
| Event Creation Assistant | `agents/event_creation_agent.py` | `POST /events/generate-content` (preview), `POST /events/{id}/generate-content` (persist) |
| Marketing Campaign | `agents/marketing_agent.py` | `POST /organizer/events/{id}/campaigns` |
| Dynamic Pricing & Promotion | `agents/pricing_agent.py` | Automatically after every `POST /bookings`; `POST /agents/pricing/reevaluate` (admin sweep); `POST /events/{id}/price-lock` |
| Fraud Detection | `agents/fraud_agent.py` | Automatically inside `POST /bookings`, before confirming |
| Customer Support | `agents/support_agent.py` | `POST /support/messages` |
| Organizer Intelligence | `agents/organizer_intelligence_agent.py` | `GET /organizer/insights` |
| Event Operations | `agents/event_operations_agent.py`, `models/operations.py` | Checklist auto-created on `POST /events`; `GET`/`PATCH /organizer/events/{id}/operations`; QR activation logged in `POST /bookings` |

## Setup

```bash
cd backend
python -m venv .venv && source .venv/bin/activate
pip install -r requirements.txt
cp .env.example .env        # defaults work as-is for local dev (SQLite)
alembic upgrade head        # create tables
python scripts/seed_data.py --reset   # optional: load the real dataset
uvicorn app.main:app --reload
```

API docs at `http://localhost:8000/docs` once running.

### Enabling real LLM generation (optional)

Without any config, Event Creation/Marketing/Support use their template
fallback. To use real generation, set in `.env`:

```
LLM_PROVIDER=anthropic
LLM_API_KEY=sk-ant-...
LLM_MODEL=<a current Claude model name from your Anthropic Console/docs>
```

### Running tests

```bash
pytest
```

### Pointing at Neon/Postgres instead of local SQLite

Set `DATABASE_URL` in `.env` (or the environment) to your Neon connection
string, e.g.:

```
DATABASE_URL=postgresql+psycopg2://user:password@ep-example-123456.us-east-2.aws.neon.tech/ticket_booking_db?sslmode=require
```

Then run `alembic upgrade head` against it before starting the app.
